## Що перевірено по суті
- **Коректність.** `pendingDiag()` (app/app.js:45) спершу відбирає предмети класу з тестом, який не пройдено й не відкладено (умова та сама, що й до правки), а потім бере предмет із найменшим `diagRank`. За рівних рангів вибір стабільний, бо в порівнянні строге `<`: перемагає перший предмет у порядку `SUBJ`. Якщо кандидатів немає, функція повертає `undefined`, як і стара `find`. Виклик один, app/app.js:779 (`pd ? {v:"diag"} : {v:"home"}`), і його поведінка не змінилася.
- **Краї:**
  - Предмет без `diagOrder` отримує ранг `Number.MAX_VALUE`, тож стоїть після предметів, у яких `diagOrder` є.
  - Якщо `diagOrder` немає в жодного предмета, лишається порядок предметів.
  - Клас без тестів дає `undefined`, і застосунок відкриває головну.
  - Предмет, у якому для класу є тест, але немає розділів, `subjectsFor()` відсікає, як і раніше.
  - `NaN`, `Infinity`, `null` і рядок validate вважає помилкою. У рушії такі значення дають `MAX_VALUE`, тобто застосунок не падає.
- **Живий зміст.** Емуляцію робив у VM: реєстр і всі файли `content/` з manifest, без браузера. Для класів 4–11 вибір падає на тест математики: dg4…dg11. Для 6 класу це `dg6`, тобто саме те, чого чекає `test-answer-ui.py`.
- **Інваріанти рушія.** Рушій не знає предметів: `if (subject === …)` немає, порядок задано даними. `SLID.subject` (app/registry.js:13) копіює всі поля метаданих через `Object.assign`. `slid.v1` не змінено, нових полів у збереженні немає. Офлайн-роботу правка не зачіпає. Build на копії дерева дав `sw.js`, `index.html`, `content/manifest.json`, `app/config.js`, побайтово ті самі, що закомічені. validate на копії: 0 помилок.
- **Документація.** CONTENT_SCHEMA §1 відповідає коду, але уточнення про відсутній `diagOrder` неповне (P3-2).

## Знахідки
- **P3-1. Сценарій 11 не перевіряє мішаний випадок: частина предметів має `diagOrder`, частина ні.** Мутант `diagRank`, у якому для предмета без `diagOrder` повертається `0` замість `Number.MAX_VALUE` (app/app.js:44), дає 105 ok / 0 ✗. Через це не зафіксовано, що предмет без `diagOrder` іде **після** предметів із ним. Новий предмет без цього поля тихо став би першим, і тест цього не помітив би. Що зробити: додати в tools/test-ui.mjs `diagOrderScenario` режим «у першого предмета SUBJ немає `diagOrder`, в інших він є». Очікування: відкривається предмет із найменшим `diagOrder`.
- **P3-2. CONTENT_SCHEMA.md:17 неоднозначно описує відсутній `diagOrder`.** Зараз там написано «без нього й за рівних — порядок предметів у збірці». За кодом предмет без `diagOrder` іде після всіх предметів, у яких він є. Варто так і написати.
- **P3-3. Пройдений тест (`S.diag[id].done`) не покрито.** Мутант, що прибирає `!S.diag[d.id]?.done` з фільтра в app/app.js:45, дає 105 ok / 0 ✗. Умова лишилася з попередньої версії, і в цьому коміті поведінка правильна. Проте задача прямо називає завершені тести краєм, а сценарій 11 перевіряє лише відкладені. Що зробити: додати в сценарій засіяний `diag: { "dgo-<min>": { done: true } }` з очікуванням, що відкриється наступний за `diagOrder`.
- **P3-4. Порядок карток на головній не узгоджено з новим порядком тестів.** Головна виводить `subs.map(planOrDiag)` (app/app.js:362) у порядку `SUBJ`, тобто за назвою файлу: hist, math, ukr, world. Після «Пізніше» на тесті математики запрошення до тесту історії стоїть вище за математику. Так само `subs[0]` для «Продовжити» (app/app.js:357) — це історія. Задача свідомо лишає це людині (P2-1, reports/qa/qa-hist-diag.md), тож розбіжність узгоджена з задачею. Коли людина ухвалить рішення щодо P2-1, картки варто сортувати тим самим `diagRank`. Окремо: docs/PERSONALIZATION.md:19 («Шлях дитини») не каже, який тест відкривається, коли їх кілька. Рядок можна дописати.
