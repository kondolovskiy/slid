## Вердикт: **потрібні виправлення**

Три P1 — усі про головний інваріант задачі «повторні синхронізації не подвоюють бали». Тристороннє злиття (`merge3`) як функція коректне. Подвоєння виникає тоді, коли клієнт втрачає `base`: після виходу чи 401 і повторного входу, після втраченої відповіді на `PUT`. Ще одне P1 стосується черги: зміна, зроблена під час запиту, губиться.

## Знахідки

### P1-1. Вихід (або 401) і повторний вхід з «Так, мій» подвоюють xp, days, skills, errs
`app/sync.js:190` (`signOut`: `st = null`) і `app/sync.js:169` (`fail(401)`: `st = null`) стирають `base`. Потім `app/sync.js:176` (`login`: `base: null, dirty: !!mine`) і `merge3(null, local, remote)` сумують лічильники. Проте локальний прогрес уже є на сервері: після виходу він лишається на пристрої (тост «Прогрес лишився на пристрої»), а після 401 картка сама просить «Увійди знову».

Відтворення (фейковий сервер, `<scratchpad>/review-sync/repro.mjs`, R1):
```
вхід «мій» xp 100 → signOut → loginGoogle(той самий, mine=true)
→ device xp 200, server xp 200, days {"d":200}, errs 2 (було 1), skills ok 6/total 8 (було 3/4)
```
Так само можна навмисно «накручувати» бали циклом «вийти → увійти → так».
**Очікувано:** повторний вхід у той самий акаунт не змінює бали. Один із варіантів: `signOut`/401 лишає в `slid.sync` `{id, rev, base}` без токена, а `login` при `r.data.id === прежній id` бере збережений `base`. Тоді приріст рахується від нього, а `merge3(base, …)` додає лише нове. Для іншого акаунта `base = null`, як зараз. Потрібен тест у `test-sync.mjs`: вихід → вхід «так» → xp без змін.

### P1-2. Втрачена відповідь на PUT (сервер записав, клієнт не дізнався) подвоює бали
`app/sync.js:146–148` і `:138`: мережева помилка чи `AbortController` на 15 с (`app/sync.js:220`) повертає `offline`, а `dirty`, `rev` і `base` лишаються старими. Наступний `PUT` зі старим `rev` отримує 409, і `merge3(старий base, local, remote)` знову додає приріст, який уже є в `remote`. Це неідемпотентний повтор. На повільній мобільній мережі тайм-аут 15 с для запису в 256 КБ цілком реальний.

Відтворення (`<scratchpad>/review-sync/repro2.mjs`):
```
вхід «мій» xp 100 → xp 150, changed → PUT записано на сервері, відповідь втрачено → {"s":"offline"}, server xp 150
→ наступний sync: 409 → злиття → device xp 200, server xp 200, days {"d":200}
```
**Очікувано:** повтор не подвоює. Варіанти: у документі є маркер запису пристрою (наприклад, `data._w = {<id пристрою>: n}`), і при 409 клієнт бачить, що його запис `n` уже прийнято, та бере надіслане як `base`. Або перед `PUT` зберігати `st.sent = {rev, data}`, а при 409 з `remote.rev === sent.rev + 1 && eq(remote.data, sent.data)` вважати запис успішним. Другий варіант не покриває запис іншого пристрою відразу після нашого, тож маркер надійніший. Потрібен тест із фейком «записав і кинув».

### P1-3. Зміна стану під час PUT не потрапляє в чергу: `dirty` скидається, хоча на сервері старіший стан
`app/sync.js:146–147`: `local` зчитано до `await`, а після 200 `st.dirty = false` ставиться безумовно. `changed()` під час запиту бачить `st.dirty === true` і лише перепланує таймер (`app/sync.js:192`). Таймер запускає `run()`, той бачить `dirty: false`, робить `GET`, отримує той самий `rev` і повертає «ok» (`:154`). Остання зміна не йде на сервер, доки не буде наступного `save()`. Якщо це був останній урок на цьому пристрої, на інших пристроях його не буде, а картка показує «Прогрес синхронізовано». Під час уроку `save()` спрацьовує на кожну відповідь, тож перекриття з `PUT` (пауза 3 с) — звичайна ситуація.

Відтворення (`repro.mjs`, R2):
```
xp 20 → changed → PUT у дорозі; під час нього save xp 30
→ local xp 30, server xp 20, dirty false; ще один sync → server xp 20
```
**Очікувано:** після 200 — `st.dirty = !eq(strip(env.getState()), st.base)` (або лічильник версій `changed`), а при `dirty` — повторна спроба. Потрібен тест.

### P2-3. Злиття й заміна стану засмічують журнал подій і тінь гіпотез

### Нова P1-4. «Скинути прогрес» → новий прогрес → вхід «Так, мій» у той самий акаунт стирає прогрес акаунта на сервері
`app/app.js:806` («Скинути прогрес») викликає `SYNC.signOut()`, тобто `drop()` (`app/sync.js:205`), а той зберігає `prev = { id, rev, base }`. Потім `login` з «так» для того самого `id` бере `rev` із `prev`. Якщо ніхто інший не писав, перший `PUT` із цим `rev` проходить compare-and-set без 409 і без злиття, і стан після скидання **замінює** документ акаунта.

Відтворення (`<scratchpad>/review-sync/repro3.mjs`, R4):
```
вхід «так» xp 100, days {d1:100} → «Скинути прогрес» (signOut + fresh) → xp 10, days {d2:10} → loginGoogle(той самий, mine=true)
→ device xp 10, server xp 10 (очікувано ≥ 110: прогрес акаунта не має зникати)
```
До виправлення цього не було: `rev 0` давав 409, а за ним злиття. Сценарій реальний: дитина скинула прогрес на своєму пристрої й увійшла знову, на питання «Це твій прогрес?» чесно відповіла «так». Наслідок — серверна втрата всього прогресу акаунта, тож це гірше за подвоєння.

**Очікувано:** «Скинути прогрес» забуває `prev` (окремий `signOut({ forget: true })` або `drop(false)`), тоді вхід іде через `rev 0`, 409 і злиття. Взагалі `PUT` з `rev` із `prev` варто робити лише тоді, коли локальний стан — нащадок `base`. Найпростіше: з `prev` брати `base` і `sent`, а `rev` лишати 0, щоб перший запис завжди проходив через 409 і `merge3`. Тоді зменшення на пристрої (скидання) не перезапише сервер, бо лічильники дають `remote + max(0, l − b)`, а done/stars — «або» й максимум. Потрібен тест у `test-sync.mjs`: скидання → +10 → вхід «так» → сервер ≥ 110, уроки акаунта на місці.
