## 2. Модель графа

### 2.1. Вузол — вміння

```js
{ id: "frac-mixed",            // нове, стабільне; ніколи не перейменовується
  sk: "frac",                  // батьківська навичка з content/subjects/math.js (обов'язково)
  name: "Перетворювати неправильний дріб на мішане число й навпаки",   // мовою вчителя, одне речення
  teach: ["m5"],               // уроки, де вміння пояснюють (1–3); порядок = програма
  pre: [{ u: "div-rem", w: 2, why: "m5 #4, #5: $11/4 = 2~3/4$ — ділення з остачею (pre: m4a)" },
        { u: "frac-read", w: 2, why: "m5 #1: правильні й неправильні дроби" }],
  part: [], same: [],
  st: "draft" }                // draft → verified → approved: статус вузла разом з його вихідними ребрами
```

- **id** — `[a-z][a-z0-9-]*`, унікальний у предметі, окремий простір імен (не збігається з `sk` і не використовується як `sk`). Рекомендовано починати з `sk` батька для читабельності, але після публікації id не змінюється, навіть якщо `sk` вузла перетеговано (як D-029).
- **Клас вузла** = клас першого уроку `teach`. Вузол без уроку (опори 1–3 кл. для baseline dg4) — `base: true, g: 3`, без `teach`.
- Вузол не вилучається: застарілий — `gone: "<новий id>"` (перенаправлення для агрегації старих даних).
- Зв'язок з наявним: `sk` — батько; урок — `teach`; тема тесту — `u` теми (§2.4). Нових ключів стану немає.

### 2.2. Ребра

| Тип | Значення | Напрям і правила | Хто використовує |
|---|---|---|---|
| `pre` w 2 | «без B типову задачу A не розв'язати» | A → B; B не пізніше за A (§3); входить у перевірку циклів | план, перевірка P гіпотез, `detect`, кабінет |
| `pre` w 1 | «B допомагає / потрібне в частині задач A» | те саме | лише підказки й кабінет; у план кроків не дає |
| `part` | B — названий крок алгоритму A (A = B₁ + B₂ …) | A → B; B не пізніше за A; входить у перевірку циклів | гіпотези (помилка в A → перевірити складову), кабінет |
| `same` | той самий прийом на іншому матеріалі (спіраль програми) | симетричне; заборонене між вузлами, з'єднаними шляхом `pre`/`part` | природні перевірки D гіпотез, кабінет («повернулося через рік») |

Сила — дискретна (1 / 2), не дробова вага: даних для калібрування немає, а 1/2 людина-вчитель може перевірити. Числові ваги — лише після пілоту з Evidence (питання 4, §7.3). Кожне ребро має `why` — конкретний екран, вправу чи пункт підручника (як `evidence` матриці).

### 2.3. Де живе граф

`content/math/graph.js`, один файл на предмет:
```js
SLID.graph("math", { v: "2026-11-15.1", nodes: [ /* §2.1 */ ] });
```
- Змінює **лише куратор** (як `plan.js` і `subjects/`, AGENTS.md §1); автори й верифікатори пропонують вузли й ребра рядком в inbox (`IDEA GRAPH: …`).
- `tools/build.mjs` уже бере всі файли `content/math/*.js` — файл потрапить у `index.html` і `sw.js` (офлайн) без змін збирача; `SLID.graph` у `app/registry.js` розв'язує посилання у `finalize()`, тож порядок завантаження не важливий.
- Розмір: ≈ 300–400 вузлів × ~250 байт ≈ 100 КБ без стиснення — менше за один великий розділ.
- Чому не в файлах уроків: вузол обслуговує кілька уроків різних класів, а одне ребро — це рішення куратора, не автора розділу; так само, як `plan.js` окремо від розділів (D-009). Чому не JSON у `docs/`: застосунку граф потрібен офлайн (план, гіпотези), а матриця v3 саме тому й не використовується рушієм.

### 2.4. Прив'язка екранів, вправ і тем тестів (`u`)

Необов'язкове поле `u` (рядок або масив з ≤ 2 id) на екрані уроку, вправі пулу, темі тесту (і, за потреби, завданні тесту). Вміння об'єкта визначає **правило виведення**:
1. Є `u` — беремо його.
2. Інакше — вузли з `sk` = `sk` об'єкта, у яких урок об'єкта (`lesson` вправи, урок екрана) є в `teach`. Рівно один — це він.
3. Boss-урок: те саме, але серед вузлів з `teach` у його розділі.
4. Тема тесту: вузли з `teach` ∩ `topic.lessons` і `sk` її завдань; baseline-тема — `u` на `base`-вузол (обов'язково).
5. Кілька кандидатів — «неоднозначно» (validate: попередження, у пілоті — помилка); жодного — об'єкт прив'язаний лише до `sk`, як зараз.

Наслідок: `u` треба ставити **лише в парах (урок, sk) з кількома вміннями** (m3 #7–9 і вправи pms1 c* «число за частиною»; g6m2l5 #7–9 і pg6m2 e* «ділення»; g6m1l4 #5) і на екранах, що тренують вміння іншого уроку. Решта — без жодної правки змісту. `u` ставить автор у своєму файлі (AGENTS.md §3 п. 5), перевіряє верифікатор.

### 2.5. Версіювання й сумісність

- `v` графа — дата + номер. Ребра й `name` можна змінювати вільно (не ключі); id вузлів — лише додавати або позначати `gone`.
- **Збережений прогрес не змінюється:** ключі SRS (урок), `S.mast` (урок), `S.skw`/`S.skills` (`math.<sk>`), `S.errs` (`l`, `at`, `sk`, `d`), `S.diag` (id тесту й теми), `S.seen` (`pool:id`) — без змін і без міграції. Стан за вузлами (§4) — **похідний**: чиста функція `SLID_LEARN.nodeState(S, graph)` рахує його щоразу з наявних записів; нічого не зберігається й не синхронізується.
- Evidence: кожна подія вже має `cv` (версія змісту з `sw.js`, туди входить і `graph.js`) і `item` (`l`, `i`, `id`, `sk`, `topic`), тож вміння відновлюється офлайн за графом тієї версії. На етапі G3 — додаткове поле `item.u` (розв'язане правилом §2.4) без зміни `v` схеми (EVIDENCE.md: нові поля додаються без нової версії).
- Обмеження: `S.errs` не пам'ятає індексу екрана, тож помилку уроку з кількома вміннями тієї самої `sk` (m3) можна приписати лише парі (урок, sk). Додавати поле в `errs` — не зараз (питання 5, §7.3).

### 5.2. Критерії

**Вузол:** (1) одне речення «учень уміє …» мовою вчителя; (2) перевіряється 1–2 завданнями без інших нових умінь; (3) пояснений у уроці `teach`; (4) має ≥ 3 прив'язаних оцінюваних екрани або вправи (інакше — злити з сусіднім); (5) типово 1–2 вузли на тематичний урок; не дрібніше за групу екранів одного правила.
**Ребро:** w 2 — крок розв'язання типової задачі A (`fbText`, `steps` вправи) використовує B; w 1 — лише частина задач; `part` — B названо як крок алгоритму A; `same` — той самий прийом (ms0l4 і g7m1l1 обидва «Терези й невідоме»). Кожне — з `why`.
**Якість лінії:** validate 0 помилок; кожне старе ребро лінії (§1.7) пояснене або відхилене з причиною у звіті; незалежний верифікатор згоден з ≥ 90 % ребер w 2 до виправлень (решту — обговорено й виправлено); жодного вузла без опори.

### 5.3. Обсяг

Увесь курс: 182 тематичні уроки, 199 пар (урок, sk) → оцінка **250–400 вузлів, 600–1000 ребер**; насіння — 343 ребра матриці, 116 `forEvidence`, 22 пари `pre`, 55 `requires`. ### 7.3. Питання людині (простою мовою; не блокують G1)

1. **Наскільки дрібно ділити?** Урок «Дріб від числа» вчить дві речі: знайти дріб від числа й знайти число за його частиною.
   а) один вузол на урок (просто, але грубо); б) **окремий вузол на кожне вміння, яке можна перевірити окремо** (1–2 на урок); в) дуже дрібно, на кожне правило.
   _Рекомендація: б._
2. **Хто остаточно затверджує зв'язки «без цього не вийде»?**
   а) лише ШІ-верифікатор; б) **верифікатор, а вчитель вибірково переглядає лінію перед тим, як рушій почне нею користуватися**; в) учитель кожне ребро.
   _Рекомендація: б (як статуси уроків: verified → approved)._
3. **Чи має граф змінювати план дитини (порядок повторення, поради)?**
   а) ні, лише для звітів учителю; б) **так, але лише в розміченій і перевіреній лінії й після порівняння «було / стало» на збережених профілях**; в) так, одразу скрізь.
   _Рекомендація: б (етап G4)._
4. **Сила зв'язку — дві градації чи числа?**
   а) **дві: «обов'язково» і «допомагає»**; б) відсотки (0,3; 0,8 …) на око; в) відсотки лише після пілоту з даними учнів.

5. **Чи запам'ятовувати, на якому саме екрані сталася помилка** (щоб розрізняти два вміння одного уроку)? Це новий запис у прогресі дитини, без зміни старих.
