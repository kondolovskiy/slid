# Дизайн: «обчислення чи поняття» — гіпотези про помилку й перевірні завдання (математика)

_Задача: tasks/doing/engine-diag-hypothesis-math.md. Етап 1 — лише дизайн, коду рушія немає. Статус: чернетка на незалежне рев'ю (D-026)._

**Рішення людини 2026-11-01:** для математики система має відрізняти помилку в обчисленні від нерозуміння поняття й пропонувати коротке завдання, що перевіряє гіпотезу; спершу детермінована логіка, LLM не обов'язковий; учнівський інтерфейс міняти не більше, ніж потрібно; дані — з Evidence V2 (docs/EVIDENCE.md).

**Коротко.** Окремий чистий модуль `app/hyp.js` (`SLID_HYP`) читає ті самі події `answer`, що пише журнал, і для кожної помилки з першої спроби відкриває гіпотезу з розподілом імовірностей по п'яти класах. Ключовий інструмент розрізнення — **перевірне завдання**: та сама тема й навичка, легші числа (обчислювальна гіпотеза передбачає «правильно», понятійна — «знову неправильно, тим самим хибним правилом»), або інша форма того самого поняття без обчислень. Спершу **тіньовий режим**: гіпотези лише журналюються, а роль перевірки грає наступна природна вправа тієї самої теми; `record`/`detect`/SRS/план/`slid.v1` не змінюються. Показ перевірних завдань дітям — окремий етап після офлайн-оцінки й рішення людини.

## 1. Модель гіпотез

### 1.1. Класи пояснень помилки

| Код | Клас | Що це означає | Що передбачає для перевірки |
|---|---|---|---|
| `slip` | неуважність / запис | метод і обчислення правильні, збій у записі: переставлені цифри, пропущена цифра, кома не там, загублений знак у кінці, не той варіант натиснуто | легша вправа ✔, інша форма ✔; друга спроба часто ✔ без підказки |
| `calc` | обчислювальна похибка | правило обране правильно, помилка в арифметиці проміжного кроку (таблиця множення, перенос, НСК) | легші числа ✔ (ймовірно), інша форма ✔; з великими числами може повторитися, але **без сталого шаблону** |
| `rule` | хибне правило / поняття | дитина застосовує систематичне хибне правило (додає знаменники, рахує зліва направо, множить показники) | легші числа ✘ **тим самим шаблоном**; інша форма ✘ |
| `pre` | незнання передумови | бракує вміння з попередньої теми (`pre`, тема `pre` тесту рівня) | вправа з уроку-передумови ✘; вправа поточної теми, де передумова не потрібна, ✔ |
| `unk` | невідомо / не знаю | «Ще не знаю», порожньо, дуже далеко від ключа, вибір без розмітки — сигналів недостатньо | нічого певного; перевірка лише зменшує невизначеність |

`form` (значення правильне, запис ні — нескорочений дріб, √576 при ключі 24, назва точки) — **не помилка розуміння**: гіпотезу не відкриває, лише лічильник `fmt` (див. §3.2). Окремий випадок — «незавершене обчислення» в тесті (√576, півбала — паралельна робота wt-half): це сигнал на користь `calc` у дуже слабкій формі, бо значення знайдено, а дію не довершено.

Пороги (2,5 с; 10 %; 50 %; 7 днів) — **початкові припущення**, не дані: їх калібрує офлайн-оцінка (§4).

### 1.3. Детерміновані правила: пріоритети й апріорні ваги

Для кожної фінальної відповіді з помилкою першої спроби (`try 1`, `verdict: "bad"`, не `hyp`) правила перевіряються згори донизу; **перше** правило, що спрацювало, задає апріорний розподіл (сума 1). S9–S12 потім множать його на коефіцієнти (§2.4) — це ті самі «лічильники», без навчання.

| Пріоритет | Умова | Розподіл slip / calc / rule / pre / unk |
|---|---|---|
| P1 | `verdict: "form"` | гіпотезу не відкривати (лише `fmt`) |
| P2 | S1 збіг з `mis`, клас X | X = 0,75, решта порівну |
| P3 | S2 мутант-правило | .05 / .10 / .70 / .10 / .05 |
| P4 | S8 повтор шаблону (без S1/S2 у цій спробі) | .05 / .10 / .65 / .15 / .05 |
| P5 | S3 знак (навичка не про знаки), S4, S5 (не meas/dec) | .60 / .20 / .10 / .05 / .05 |
| P6 | S5 при `sk` meas/dec, S3 при навичці про знаки | .15 / .10 / .60 / .10 / .05 |
| P7 | S6 близькість | .20 / .55 / .15 / .05 / .05 |
| P8 | S7 ±1 у лічбі | .15 / .35 / .40 / .05 / .05 |
| P9 | S13 | .00 / .05 / .15 / .30 / .50 |
| P10 | S14 або нічого | .10 / .15 / .25 / .15 / .35 |

Після апріорного кроку — модифікатори: S12 → `pre` × 2,5; S9 → `rule`, `pre` × 0,5; S10 «ок без підказки» → `slip`, `calc` × 2; «ок лише після підказки» → `rule` × 1,5; «✘ після підказки» → `rule`, `pre` × 1,5; S11 «швидко» → `slip` × 1,5. Потім нормування. Відповідь гіпотези — `top` (найімовірніший клас) і `p` (його ймовірність); якщо `p < 0,45` — `top = unk`.

**Узагальнений висновок для дитини/плану** (§2.5) спирається на двоклас: `exec` = slip + calc («обчислення/запис») проти `know` = rule + pre («поняття/передумова»). Саме його вимагає рішення людини; п'ять класів — для діагностики й аналізу.

## 2. Перевірні завдання

### 2.1. Види перевірки

| Вид | Що перевіряє | Звідки брати | Передбачення exec / know |
|---|---|---|---|
| **E — легші числа** (та сама структура) | обчислення: якщо правило правильне, легкі числа не підведуть; хибне правило повториться тим самим шаблоном | пул того самого уроку й `sk`, `lvl` 1, найменші числа; з `gen` — набір з мінімальними значеннями | ✔ / ✘ (і часто той самий `mis`/мутант) |
| **F — інша форма** (без обчислень або з тривіальними) | поняття: choice/multi/comparison про саме правило | choice/multi пулу того самого уроку; екрани уроку `choice` з тим самим `sk` (напр. g8m1l2#7 «Олег пише $1/x + 2/x = 3/(2x)$»), comparison (pg7m3:a05) | ✔ / ✘ |
| **P — передумова** | `pre` проти `rule` | пул уроку `pre` (поле вправи) або уроків теми тесту рівня зі статусом `gap/shaky`, `lvl` 1 | при `pre`: ✘; при `rule` поточної теми: ✔ |

**Добір (детермінований):** кандидати — `practiceItems` (лише відкриті теми, як і зараз), без вправ, бачених у цій сесії, і без самої вправи з помилкою. Сортування: (1) вид за гіпотезою — `top ∈ {slip, calc}` → E; `rule` → F, якщо є, інакше E; `pre` → P; `unk` → E; (2) `S.seen[key] === undefined` раніше за бачені; (3) «легкість» = сума кількості цифр чисел у `title`/`body` + цифр ключа (менше — легше); (4) порядок у пулі. Без кандидата — гіпотеза лишається відкритою до природної перевірки (§2.3).

**Покриття сьогодні:** E можливе для 158 зі 169 уроків з пулом (≥ 2 вправи `answer` рівня 1), F — для 47 уроків з choice/multi у пулі (плюс choice-екрани уроків), P — лише там, де є `pre` (30 екранів уроків) або тест рівня з темами `pre`. Тобто «поняття» найслабше покрите формою F — це аргумент за розмітку (§5), а не за масову зміну змісту.

### 2.2. Скільки й коли (у режимі показу, етап E5)

- Лише в **тренуванні** (`run.practice`). Не в уроці (не подовжувати маршрут, урок і так має підказку й другу спробу) і не в тесті рівня (без фідбеку; тест — фіксований набір і `rev`).
- Тригер — фінальна подія `answer` з помилкою першої спроби, якщо гіпотеза відкрита з `p ≥ 0,45` і для неї є кандидат. Перевірна вправа вставляється **наступною** в сесію (не замінює заплановані).
- Не більше **1 перевірки на гіпотезу** і **2 на сесію**; не вставляти, якщо наступна запланована вправа й так та сама пара (урок, sk) і рівень ≤ — тоді вона й є перевіркою (природна).
- Учнівський інтерфейс: та сама картка `answer`/`choice`, лише `eyebrow` «Ще одна, коротка» (формулювання — людині). Жодних ярликів «ти не розумієш» ніде в UI; гіпотеза дитині не показується.

### 2.3. Тіньовий режим (етапи E2–E4): природна перевірка

Нічого не вставляємо. «Перевіркою» вважаємо першу наступну відповідь (у цій або наступній сесії, ≤ 7 днів) на ту саму пару (урок, sk) з `lvl` ≤ рівня вправи з помилкою — `pickSession` дає їх часто, бо бере 4 вправи теми від легшого рівня. Вправа іншої форми (choice/multi) того самого уроку — природна перевірка F. Відповідь на уроці `pre` — природна P. Умова `lvl ≤` прибирає головне зміщення: наступна складніша вправа, розв'язана неправильно, нічого не каже про обчислення.

### 2.4. Оновлення гіпотези (лічильниковий байєс)

Ймовірність результату перевірки за класом (початкові припущення для калібрування):

| P(перевірка ✔ \| клас) | slip | calc | rule | pre | unk |
|---|---|---|---|---|---|
| E — легші числа | .90 | .85 | .20 | .25 | .50 |
| F — інша форма | .90 | .90 | .25 | .35 | .50 |
| P — передумова | .90 | .90 | .75 | .20 | .50 |

Оновлення: `post(h) ∝ prior(h) · L(результат | h)`; якщо помилка перевірки збіглася з тим самим `mis`/мутантом, що й вихідна, `L(✘ | rule)` множиться на 2 (повтор шаблону — найсильніший доказ). **Закриття** (`hyp_close`): `max(post) ≥ 0,8` (→ `confirmed`), або 2 перевірки без порогу (→ `undecided`), або 7 днів без перевірки (→ `expired`), або урок/тема пройдені знову з ≥ 65 % (→ `superseded`). Числа L — не «істина», а параметри; їх перевіряє калібрування на журналі (§4).

### 2.5. Вплив на SRS і план

| Етап | record / detect / SRS / план | Що робить модуль |
|---|---|---|
| E1–E4 (тінь) | **без змін**; `slid.v1` байт-у-байт той самий, що без `app/hyp.js` (регресія як у Evidence) | лише події `hyp_*` у журналі |
| E5 (показ) | перевірна відповідь **не** йде в `record`, `S.seen`, `srsUpdate` і `run.graded` (щоб перевірка не змінювала прогрес); XP — як за звичайну вправу (обговорити) | вставка вправи; `hyp_probe` із `shown: true` |
| E6 (після рішення людини) | варіанти: `exec` підтверджено → помилка рахується в `detect` з вагою ½ і не скидає коробку на 0, а знижує на 1; `rule` підтверджено → крок плану `src: "hyp"` на урок, де правило пояснено; `pre` → крок на урок `pre` (як `src: err`) | — |

### 3.3. Версіювання

- Схема подій лишається `v: 1`: нові типи й поля в `d` — дозволене розширення.
- `rv` — версія правил і параметрів (`hyp-1`, `hyp-2`…). Будь-яка зміна порогів, апріорних ваг, L чи каталогу мутантів → нова `rv`, запис у docs/design і в `app/hyp.js` (`RULES_VERSION`). Офлайн-реплей уміє перерахувати старий журнал новою `rv` — так порівнюємо версії на тих самих даних.
- `mis` у змісті не міняє `rev` тесту рівня (вердикт не змінюється), але міняє `cv` — реплей бере розмітку тієї `cv`, яка була в події.

## 4. Метрики якості й план перевірки

### 4.1. Офлайн-оцінка на журналі

Інструмент `tools/hyp-replay.mjs`: вхід — експорт `SLID_EVIDENCE.export()` (JSON) + дерево змісту; вихід — `reports/hyp/<дата>.md` і JSON. Той самий `app/hyp.js`, що в застосунку (як `test-learn` вантажить `learn.js`).

| Метрика | Визначення | Навіщо |
|---|---|---|
| Покриття | частка помилок першої спроби з `top ≠ unk` | чи бачить модель хоч щось |
| Розв'язність | частка гіпотез із перевіркою (природною чи вставленою) за 7 днів | чи є на чому оцінювати |
| **Точність exec/know** | серед закритих з перевіркою: `top ∈ exec` і перевірка ✔ або `top ∈ know` і ✘; матриця 2×2 і по класах | головна метрика рішення людини |
| Калібрування | Brier і графік надійності для передбаченої P(перевірка ✔) | чи можна вірити `p` |
| Хибна тривога «поняття» | `top ∈ know` з `p ≥ 0,6`, а наступні 3 відповіді першої спроби на ту саму пару ✔ | найдорожча помилка: дитину «лікують» без потреби |
| Пропущене поняття | `top ∈ exec`, а наступні 2 з 3 ✘ тим самим шаблоном | |
| Порівняння з базовими | «завжди calc», «завжди rule», «лише detect» (тема просіла → know) | модель має бути кращою за найпростіше правило |
| Ціна (E5) | вставлених перевірок на сесію, `dt` перевірки, частка `close` з `end: false` одразу після перевірки проти без неї | чи не втомлює |

**Обмеження оцінки:** природна перевірка й мітка — те саме джерело (наступна відповідь), тож точність буде завищеною для класів, що й так «вирішуються часом». Тому (1) порівнюємо лише з базовими на тих самих парах, (2) на пілоті — **золота вибірка**: 100–200 помилок з `raw` і умовою, які вчитель розмічає вручну (exec/know), не бачачи гіпотези.

### 4.2. Поетапна перевірка перед показом дітям

1. **Фікстури** (E1): синтетичні журнали з реальних вправ §1.5 (по 2–3 записи на кожен сигнал) — модульні тести, не оцінка якості.
2. **Тінь на QA-прогонах** (E2): `playtest.py`/`test-answer-ui.py` з навмисними помилками — перевірка «труб» (події пишуться, `slid.v1` незмінний). Агенти — не діти: якість тут не міряємо.
3. **Тінь на пілотних пристроях** (E4): діти пілоту (разом з research-math-diag-duration), згода дорослих, експорт консоллю дорослим (кнопки експорту немає — окреме питання людині). Орієнтир обсягу — ≥ 300 закритих гіпотез з перевіркою. Поріг переходу до E5 (пропозиція): точність exec/know ≥ 0,7 і краща за найкращу базову ≥ на 0,1; хибна тривога «поняття» ≤ 20 %; згода з золотою вибіркою (κ) ≥ 0,5.
4. **Пілот показу** (E5): прапорець, типово вимкнений; частина пристроїв пілоту; порівняння ціни й точності з тінню.

## 5. Що потрібно від змісту: пропозиція `mis` (CONTENT_SCHEMA)

Необов'язкове поле завдання (екран уроку, завдання тесту §9, вправа пулу §10) — **типові хибні відповіді та їх пояснення-клас**. Масової зміни змісту не пропоную: лише пілот (dg6, pg6m2, pg7m3 — ≈ 25 завдань) задачею автора з верифікатором.

```js
// choice: за індексом варіанта (решта — без розмітки)
{ type: "choice", sk: "ops", title: "$3/8 + 2/8 = ?$", opts: ["$5/16$", "$6/8$", "$1/8$", "$5/8$"], correct: 3,
  mis: { 0: "rule:frac-add-naive", 2: "slip:op" } }
// answer / number: за значенням (порівнюється як ключ, тим самим checkAns)
{ id: "d01", type: "answer", title: "$1/4 + 3/5$", answer: "17/20", reduced: true, mixed: true,
  mis: [ { v: "4/9", c: "rule:frac-add-naive" }, { v: "3/20", c: "rule:frac-mul-num" } ] }
// передумова як пояснення помилки (g11m6l1#5, pre: g10m3l2 «Дробовий показник»)
  mis: { 0: "pre:g10m3l2", 2: "rule:neg-exp", 3: "slip:sign" }
// корінь як хибна відповідь до числового ключа (pg8m4:b02, ключ 9): порівнюється як exactRoot
  mis: [ { v: "√369", c: "rule:pyth-add" }, { v: "3", c: "rule:pyth-linear" } ]
```

- `c` — `slip|calc|rule|pre` + `:` + код. Код `rule:*` — з каталогу правил математики (кандидат у memory/long/glossary/math.md, розділ «Типові хибні правила»; вносить куратор), `pre:<id уроку>` — існуючий урок.
- Валідатор (етап E3): `v` не збігається з ключем (`checkAns(s, v) === "bad"`, тобто ні ok, ні form) і сам розбирається як відповідь того самого `answerKind` (`checkAns({ ...s, answer: v }, v) === "ok"`; для числового ключа запис із коренем — як `exactRoot`); індекси choice в межах `opts` і ≠ `correct`; `pre:` — урок існує й раніший за програмою; ≤ 4 записи; `mis` не показується дитині і не впливає на вердикт (тест на незмінність `checkAns`).
- Автору: брати хибні відповіді з `fbText`, підручника («типові помилки» в методичних примітках) чи з журналу пілоту, **не вигадувати** «правдоподібних» — та сама вимога точності, що й до фактів.
- Для `gen` (коли з'явиться) `mis` — вирази над змінними (`{ e: "(a+c)/(b+d)", c: "rule:frac-add-naive" }`), той самий синтаксис, що `gen.answer`.

## 7. Історія: перенесення архітектури (без реалізації)

Та сама схема «сигнали → класи → перевірка → оновлення» без змін рушія гіпотез; змінюються лише каталог сигналів і класів. Типи екранів історії — choice, order, sort; `sk` уже ближчі до навичок: `time` 226, `src` 212, `civ` 216, `crit` 345, `geo` 130, `cult` 69, `date` 10.

| Навичка | Класи (аналоги) | Сигнали | Перевірка E / F / P |
|---|---|---|---|
| **Хронологія** (`time`, `date`) | `slip` (переплутав сусідні); `rule` — хибне правило лічби (століття = перші дві цифри; роки до н. е. «вперед»; рік 0); `pre` — не знає самої дати (факт) | order: перестановка сусідніх → slip, повна інверсія частини до н. е. → rule; choice з `mis`: s1 l3#3 (1648 → «XVI ст.» = `rule:century-digits`), l3#5 (500 р. до н. е. → 500 р. н. е.: «1000 років» = `rule:year-zero`), l3#1 («1000 р. до н. е. давніше» = `rule:bc-forward`) | E — те саме правило на інших датах (інше століття); F — розташувати 3 дати на стрічці; P — факт іншої форми («коли…?») |
| **Аналіз джерел** (`src`) | `rule` — плутає першоджерело й пізніший опис, факт і оцінку автора; `pre` — не знає контексту епохи; `slip` | sort (кошики «джерело/дослідження», «факт/думка»): усі помилки в один бік → rule; одна → slip | E — те саме розрізнення на іншому тексті; F — choice «хто автор / коли створено» |
| **Причини й наслідки** (`civ`, `crit`) | `rule` — інверсія причини й наслідку, «після — отже через»; `pre` — не знає подій ланцюжка | order/sort: обмін місцями причини й наслідку → rule; помилка лише там, де подія не з уроку → pre | E — інший ланцюжок того самого розділу; P — питання про подію-передумову |
| **Аргументація** (`crit`) | `rule` — аргумент без доказу, доказ не до тези; `slip` | choice з `mis` за типом хибного аргументу | F — вибрати доказ до готової тези |

Відмінність від математики: «легших чисел» немає, тож вид E — «той самий прийом на іншому матеріалі»; клас `pre` частіше означає **незнання факту**, а не вміння, і перевіряється питанням на факт з реєстру (memory/long/facts/hist.md). Розмітка `mis` для історії особливо корисна, бо мутантів рушія тут не буде.
