# Журнал подій (Evidence V2)

Структурована історія того, що робила дитина: які екрани бачила, що й коли відповідала, чим закінчився урок, тренування чи тест рівня, як змінювалися коробки SRS, план і клас. Навіщо: без таких даних не перевірити якість жодного діагностичного алгоритму (Skill Graph, Diagnostic Engine, ШІ-перевірка, Teacher Dashboard). Рішення людини 2026-11-01, пріоритет 1 (задача engine-evidence-v2).

Модуль — `app/evidence.js` (`window.SLID_EVIDENCE`). Тести: `node tools/test-evidence.mjs` (вузлові) і `evidence_checks` у `python3 tools/test-answer-ui.py --suite regression` (браузер).

## Що журнал НЕ змінює

- Поточний стан лишається в `localStorage` `slid.v1`; `record()`, `detect()`, SRS, план, тест рівня журнал лише **читає**. Регресійний сценарій проходить той самий маршрут з IndexedDB, без неї і без модуля — `slid.v1` однаковий.
- Учнівський інтерфейс не змінюється: кнопки експорту немає (лише консоль, див. нижче).
- Без IndexedDB (приватний режим, старий браузер, заблоковане сховище, `file://` з обмеженнями) або без самого файлу `app/evidence.js` застосунок працює як раніше; події тихо губляться.
- Нічого не йде в мережу.

## Як це працює

- `log(type, data)` — синхронний виклик, нічого не повертає й ніколи не кидає. `data` — об'єкт або функція без побічних ефектів; функцію журнал викликає одразу в `try/catch` (помилка губить лише цю подію) і робить копію даних на цей момент.
- Події стають у чергу в пам'яті й пишуться в IndexedDB пакетами (`LIMITS.batch` = 40) через ≈ 1,2 с, а також при `pagehide` і коли вкладка ховається. Подія, записана менш ніж за секунду до закриття вкладки, може загубитися.
- База `slid-evidence` (версія 1): сховище `events` (ключ `seq`, індекс `synced`) і `meta` (`did`, `pid`, `seq`).
- Підключення в `app/app.js` — тонкі виклики `EV.log(...)` у місцях, де події вже є, і `EV.observe(S)` після кожного `save()`; якщо модуля немає, `EV` — заглушка.
- Ротація: коли подій більше за `LIMITS.max` (15 000), найстаріші видаляються, лишається `LIMITS.keep` (13 500). Подія ≈ 0,3–0,6 КБ, тож це ≈ 5–9 МБ; завелика подія (> 2 КБ JSON) зберігається з `d: { trunc: true, keys }`. Рядки обрізаються до 300 символів, масиви — до 60 елементів.
- Збої: невдале відкриття бази вимикає журнал; невдалий запис губить пакет, три поспіль — вимикають журнал до перезавантаження. Черга в пам'яті — не більше 1000 подій (старі витісняються).

## Схема події (версія 1)

```js
{ v: 1,              // версія схеми
  seq: 42,           // наскрізний лічильник пристрою (монотонний, призначається під час запису в одній транзакції з meta.seq)
  type: "answer",    // тип (нижче)
  t: 1793553165569,  // локальний час, мс від епохи (Date.now)
  tzo: -120,         // зсув часового поясу, хв (getTimezoneOffset)
  n: 4,              // номер події в межах сесії (завантаження сторінки)
  ms: 459,           // performance.now(), мс від завантаження — монотонний у межах сесії
  sid: "…",          // id сесії (випадковий, новий при кожному завантаженні)
  did: "…",          // анонімний id пристрою (випадковий, у meta; не змінюється)
  pid: "…",          // анонімний id профілю (новий після «Скинути прогрес»)
  cv: "53ce7ea4aa",  // версія змісту = VERSION активного sw.js; null без service worker
  net: 1,            // navigator.onLine у момент події (1/0)
  synced: 0,         // для майбутньої синхронізації: 0 — не надіслано
  by: 3,             // лише srs / plan / grade: n явної події, після якої сталася зміна
  dt: 1200,          // лише answer: мс від показу екрана до цієї спроби
  d: { … } }         // дані типу
```

**Коміт змісту.** `cv` — хеш файлів застосунку з `sw.js`. Коміт, у якому з'явилася ця версія: `git log -S'VERSION = "<cv>"' --oneline -- sw.js`. Окремого поля з комітом немає: `sw.js` генерується до коміту, і хеш коміту в ньому зробив би збірку невідтворюваною (CI порівнює `sw.js` після `build`).

**Приватність.** Ім'я (`S.name`) і будь-які поля профілю, крім класу, у журнал не потрапляють; регресія перевіряє, що ім'я з `slid.v1` відсутнє в експорті. Сирий запис відповіді (`raw`) — те, що дитина ввела в поле відповіді (до 300 символів).

### Типи подій і `d`

Опис екрана/вправи `item` (у `screen` і `answer`): `{ mode: "lesson"|"practice"|"diag", c — предмет, l — урок (у тренуванні — урок вправи; у тесті — id тесту), i — індекс екрана/завдання, id — id вправи пулу, key — "пул:вправа", pool, type, ak — answerKind, sk, pre, topic — тема тесту, rev — редакція завдання тесту, boss, hyp — poll/hyp без оцінки }`.

| type | коли | d |
|---|---|---|
| `boot` | завантаження застосунку | `grade, subj, lessons` (скільки), `diags` (id завершених), `srs` (скільки) |
| `screen` | показ екрана в плеєрі | `item` |
| `answer` | кожна спроба (натискання «Перевірити»/«Відповісти», «Ще не знаю») | `item` + `try` — номер спроби, `verdict` — `ok`/`form`/`bad` (answer: `checkAns`; інші типи: ok/bad), `hyp` (poll/hyp), `skip` (тест); `raw` — сирий запис (число/рядок, індекс варіанта, масив для multi/sort/order/shade, стан лабораторії); `hint` — чи була показана підказка до цієї спроби; `final` — спроба закриває екран; у тесті ще `res` — збережений вердикт (1/0/−1) |
| `lesson_start` / `lesson_end` | початок / підсумок уроку | `c, l, sec, grade, boss, linked, screens` / `acc, stars, first, graded, mistakes, xp, closed` (закриті кроки плану), `retry, recs` (порада detect), `steps` (нові кроки), `weak` |
| `practice_start` / `practice_end` | сесія тренування | `focus, prN, items: [{key, l, review, lvl}]` / `res: [{lesson, ok}], first, graded, xp, srs` (результат srsUpdate), `recs, steps` |
| `diag_start` / `diag_end` | тест рівня | `diag, grade, rev, items, resumed` / `res, topics, steps, base, known` |
| `close` | закриття плеєра | `mode, l, i, of, end` (дійшов до підсумку чи вийшов раніше) |
| `srs` | після `save()`, якщо змінилися коробки | `n, ch: [{l, from, to}]` (до 40 змін), `from/to` — запис `S.srs[l]` або null |
| `plan` | після `save()`, якщо змінився план предмета/класу | `c, grade, diag, steps: [{l, src, why, done}], base, known` (скільки) |
| `grade` | перемикання класу | `from, to` |
| `reset` | «Скинути прогрес» (наступні події — з новим `pid`) | — |

Перший `observe` після завантаження — лише знімок; зміни, які робить сам рушій під час старту (наприклад, `planFor` переносить старий план), приходять подіями з `by` = n події `boot`. Після перемикання класу `S.plan` міняється місцями з `planByGrade`, але подія `plan` з'являється лише для справжніх змін (план ключується за предметом і класом).

## Версіювання

- `v` — версія схеми події. Додати нове поле в `d` чи новий тип — **без** зміни `v` (читачі ігнорують невідоме). Перейменувати чи змінити зміст наявного поля — `v + 1` і опис тут; старі події не переписуються.
- Версія бази IndexedDB (`DB_VER`) змінюється лише зі структурою сховищ; міграція — в `onupgradeneeded`.

## Як читати

У консолі браузера (на пристрої дитини, лише для дослідження):

```js
await SLID_EVIDENCE.stats()     // { enabled, count, unsynced, first, last, firstT, lastT, queued, dropped, did, pid, cv }
await SLID_EVIDENCE.export()    // { schema, app, exportedAt, did, cv, dropped, events: [...] } у порядку seq
await SLID_EVIDENCE.download()  // зберігає slid-evidence-<дата>.json; повертає кількість подій
await SLID_EVIDENCE.clear()     // стерти журнал (стан застосунку не чіпає)
```

Приклади аналізу: частка `form` серед спроб за `ak`; спроби до `final` і `hint` на екранах уроку; `dt` першої спроби; де `close` з `end: false` (кидають урок); `srs` між сесіями тренування; кроки `plan` від `diag_end` до їх закриття в `lesson_end`.

## Межі й відкрите

- Кнопки експорту в профілі немає — це зміна інтерфейсу, потрібне рішення людини.
- Синхронізації немає; `synced` і індекс за ним — заготовка (Teacher Dashboard після синхронізації, окремі дозволи).
- `observe` бачить лише зміни, що дійшли до `save()`; проміжні стани в межах одного кроку не журналюються.
