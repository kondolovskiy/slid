# Перевірка персоналізації

Інструменти працюють на частковому наборі контенту. Матриця `docs/math-personalization-coverage.json` визначає required-уроки, пули, формати й кількості; optional/pending мають окремі списки. Поточна версія — 2026-11-04.v7 (розділи «Зміни v7», «Зміни v6», «Зміни v5» і «Зміни v4» матриці; v3 — «Зміни v3»): 52 розділи / 234 тематичні уроки, 199 required / 48 пулів, 11 optional / 24 pending, 8 діагностик. Новий урок без пулу — pending (`poolState: deferred`, вправ 0–0): він у матриці (інакше «Урок поза матрицею»), але не входить у знаменник покриття, мінімум вправ і strict. Коли урок і його пул verified, наступна версія матриці переводить рядок у required (формати D-028 — з нотаток автора пулу й звіту верифікатора; v6 — 5–6 кл., v7 — 7–8 кл.) або optional (за рішенням людини, як g6m6).

```bash
# Без браузера й залежностей: інвентар, посилання, джерела, навички, рівні, покриття
node tools/personalization-qa.mjs
node tools/personalization-qa.mjs --grade 6
node tools/personalization-qa.mjs --diag dg6
node tools/personalization-qa.mjs --pool pg6m2 --json

# Суворе приймання всього required-пакета або одного класу
node tools/personalization-qa.mjs --strict
node tools/personalization-qa.mjs --grade 6 --strict

# Браузер: потрібні Playwright та Chromium
python3 -m pip install playwright
python3 -m playwright install chromium
python3 tools/test-answer-ui.py --grade 6
python3 tools/test-answer-ui.py --suite content --diag dg6
python3 tools/test-answer-ui.py --suite content --pool pg6m2
python3 tools/test-answer-ui.py --suite regression
python3 tools/test-answer-ui.py --strict

# Уже встановлений Chrome можна обрати без завантаження Chromium
python3 tools/test-answer-ui.py --browser '/Applications/Google Chrome.app/Contents/MacOS/Google Chrome' --grade 6
# Без --browser (і SLID_BROWSER) — як playtest.py: спершу /opt/pw-browsers/chromium, якщо він є (PW_DEFAULT=1 вимикає), потім Chromium Playwright

# Самоперевірка QA-інструмента та чистої логіки рушія; входять у check/CI
node tools/test-personalization-qa.mjs
node tools/test-learn.mjs

# Диференційна регресія перевірки відповідей: старий app/learn.js (git-ревізія) проти поточного
node tools/diff-answers.mjs                 # типово --old 1b3819d (до engine-math-answer-kinds-new), класи 4–9
node tools/diff-answers.mjs --old <rev> --grades 4-11 --time --show 20
```

`test-personalization-qa.mjs` перевіряє лічильники, optional/pending, рівні, формати, навички, прив'язки проб діагностики, baseline і винятки `exactRoot`/`expression` на **синтетичній фікстурі** (власні предмет і матриця в самому тесті: 4 розділи, 10 уроків, 3 пули, 2 тести рівня), а не на живому змісті: новий пул, вправа чи урок у `content/` не ламають тест і CI. Живий зміст там — лише як предмет перевірки: 0 структурних помилок, `--strict` узгоджений зі звітом, коди виходу CLI.

`diff-answers.mjs` проганяє всі вправи, які перевіряє `SLID_LEARN.checkAns` (пули, `fracin hideDen` діагностик, екрани `answer` уроків), — ключ і типові рівні/хибні записи (пробіли, «−», крапка, ±1, переставлені елементи, префікси, свої/чужі одиниці, періодичний дріб…) — старою й новою версією й порівнює вердикт і текст підказки. Кожна розбіжність має належати дозволеній категорії; класифікація незалежна від реалізації (стару версію перевіряють на «очищеному» записі). Непояснена розбіжність або ключ, який нова версія не приймає, — rc 1. `--time` друкує найгірший час checkAns + підказки на важких записах. `--grades 4` — один клас (те саме, що `4-4`); порожнє чи хибне значення (`4-`, `11-4`) — rc 2, а не прогін 0 вправ. Категорія «uh …» (engine-unit-hint) — лише текст підказки: «Перевір одиницю» замість звичайного повідомлення, коли запис — та сама величина в іншій одиниці (власна таблиця одиниць інструмента), вердикт `bad` той самий. «uh-p3 …» (engine-unit-hint-p3) — для тих самих записів хвіст «Одиницю можна й не писати» → «Перевір одиницю: переведи відповідь у …».

**Самоперевірка `tools/test-diff-answers.mjs`** (у `npm run check` і CI): `--old HEAD` (вердикт↔вердикт, на чистому дереві — 0 змін); фікстура «старого» `learn.js` з відомою різницею `diagVerdict` (різниці мають бути НЕПОЯСНЕНІ без категорій half і давати rc 1); `learn.js` до half-credit (`tools/fixtures/learn-b799dfa.js` — дослівна копія з b799dfa: усі HALF пояснені); `--content-old` (поле `u`). Старі версії комітяться в тимчасовому git-репозиторії з копією `app/`, `content/`, `tools/`, тож тест не залежить від історії проєкту — працює в неглибокому клоні (`fetch-depth: 1` у CI) і після squash-злиття, де b799dfa в `main` немає (рев'ю tools-diff-answers-p3, P2-1). **Правило:** частина «до half-credit» вимагає rc 0 від усього `diff-answers`, тож будь-яка навмисна зміна вердиктів `checkAns` чи `diagVerdict` потребує нової категорії в `diff-answers.mjs` (з класифікацією, незалежною від реалізації), інакше `npm run check` і CI червоні — це так задумано.

`--grade`, `--diag`, `--pool` обмежують реальний контент. `--diag` і `--pool` взаємовиключні; клас можна поєднати з одним із них. Невідомий аргумент/id, порожній перетин, відсутні доступні об’єкти та непідтриманий драйвер відповіді завершують команду помилкою. `--suite regression` запускає контрольовані fixtures і не приймає фільтрів контенту. Типово `all` запускає реальний набір та fixtures; `content` — лише реальні об’єкти. Браузер друкує кількість діагностик, пулів і справді перевірених вправ.

Звичайний режим блокує структурні помилки доступного контенту, але дозволяє незавершений пакет і повідомляє прогалини. `--strict` додатково блокує відсутній required-контент, незавершену незалежну верифікацію, відсутні рівні/формати/навичку з матриці та непідтримані сценарії. Повний суворий режим зараз **має падати**. Це окремо від успішного технічного прогону чинних dg6/pg6. Винятки кількості беруться з `exercises.min/max` і пояснення рядка матриці; три рівні потрібні для кожного required-уроку. Навички (`sk`) — за правилом нижче.

**Навички (`sk`), рішення людини 2026-10-31 (engine-math-skill-sync).** Джерело правди — навички, які урок справді тренує, тобто `sk` його екранів. `sk` рядка матриці — рядок або масив (масив — лише коли урок справді тренує кілька навичок і пул має їх усі; інакше досить одного значення) і має бути оголошений у `skills` предмета, інакше помилка (для кожного рядка — і без пулу, і optional/pending). Кожен `sk` рядка має бути серед `sk` екранів уроку: для required розбіжність — прогалина strict (`sk матриці … не тренує урок`), для optional/pending — попередження. `--strict` вимагає, щоб у пулі уроку була вправа з кожним `sk` рядка (`немає навички матриці …`). Вправа пулу чи проба діагностики (за `item.lesson` або єдиним уроком теми), чий `sk` не входить у `sk` екранів її уроку, дає `ПОПЕРЕДЖЕННЯ` — не помилку і не прогалину: так позначено вправи, що справді тренують суміжну навичку (напр. pg8m6 a06 — сторони за периметром, `meas`, в уроці сум кутів `geom`). Ставити `sk` вправі лише заради збігу з матрицею не можна: тег відповідає змісту вправи. Коли `sk` вправ змінюють, журнал помилок збереженого прогресу переносить `SLID_LEARN.migrateSk` (правила `SK_RETAG`, звірені з контентом у `test-learn.mjs`).

Для діагностик звіряються також `itemSkills` і `itemLessons` у порядку проб кожної теми. Неявна прив’язка до єдиного уроку теми еквівалентна явному `item.lesson`; для теми з двома уроками пропущена прив’язка не проходить strict. Індекси проб `itemIndices` звіряються там, де їх зафіксовано в матриці (зокрема для збережених відповідей dg6).

У тесті діагностики виконуються всі правильні відповіді, справжня базова помилка з пропуском складнішої, shaky та «Ще не знаю». Кожен сценарій перевіряє «Пізніше», збереження/відновлення після першої відповіді та початок повторного тесту. До завершення тесту фідбек, підказки, лічильники-відповіді, зміни XP/комбо/навичок/журналу помилок заборонені. Наявні 20 XP за завершення тесту — окрема чинна поведінка рушія.

Кожна реальна вправа пулу проходить звичайний екран і перевірку відповіді; перевіряються `seen`, кроки, джерело, недоступність тем до уроку й доступність після запису пройденого уроку. Для повного обходу пул тимчасово обмежується порціями до шести вправ у пам’яті браузера. Запис пройдених уроків тут — fixture; повне проходження справжнього ms2l4 уже є в сценарії міжкласового контексту. Реальний пул 5 класу залишається для фінального приймання після його авторства.

Після кожної порції перевіряються SRS, збереження й завантаження офлайн через справжній service worker, потім відкривається тренування без мережі. Сервер має вільний локальний порт. Час календаря зафіксовано на 16.10.2026 для нових контентних і сесійних сценаріїв. Fixtures сесії перевіряють 4 + 2 з двох тем повторення, пріоритет небачених над помилковими/успішними, hint і другу спробу, перехід повторюваних помилок у план, малий/вичерпаний/порожній пул, зростання й скидання SRS. Решта граничних випадків пріоритетів і дат — `test-learn.mjs`.

Регресії плеєра з приймання 4–5 класів (`player_qa_checks`, fixtures): підсумок тренування, уроку й тесту відкривається з верху після довгого прокрученого екрана; друга спроба можлива лише після зміни відповіді (поле й вибір варіанта; повторний Enter і клік не витрачають її); після перевірки фокус на «Далі», а фон плеєра inert (Tab не виходить за межі); «Джерело:» без подвоєння сторінки; кнопки числового поля за класом і ключем; «Продовжити» на головній узгоджено з планом і `known`.

Драйвер повторює порядок уроків застосунку при однакових датах SRS; окрема браузерна регресія містить два уроки у зворотному порядку з різними відповідями. Автори пулів можуть вільно перемішувати вправи різних уроків у файлі.

Додавання класу не потребує нового раннера: зареєструвати diag/pool і запустити `--grade N`. Для нового типу екрана розширити `answer_context_screen`; невідомий тип викликає помилку. Для реальної базової помилки наразі драйвер підтримує number/choice на першій pre-темі; новий тип потребує явного доповнення. Контракт baseline 4 класу підтримано (engine-math-diag-g4-baseline): інвентаризація звіряє прапорець `baseline` з матрицею, `diagnostic_checks` для baseline-передумови перевіряє `plan.base` без кроків, а fixture dg4 у regression — підсумок, «До першого уроку», план і повторний тест; `baseline_compat_checks` — план, збережений версією PR #6 з `base[].l` замість `next`, і далі веде на урок. Драйвер вводить ключ `quantity` складеним записом (`SLID_LEARN.ansText`: «2 м 45 см»). `divrem_checks` — ділення з остачею (підказка «допиши остачу», кнопка «ост.», нульова остача, показ ключа). Символьні формати (ratio, coordinates2/3, exactRoot, intervalSet, expression, periodicSet; list із коренями) і формати 2026-10-31 (`time`, `quantity` з `form: "compound"`, `decimals`, `form: "improper"`, `multiset`, префікси `AB =`/`x =`, періодичний дріб, «60 грн.») мають регресію в цьому самому файлі (`answer_format_checks`): fixture-пул проводить кожен формат через справжній екран — перша спроба з неправильним або неспрощеним записом (підказка «form»), друга з еквівалентним записом іншого вигляду; вставка кнопкою в місце курсора (зокрема «:» для часу), кнопки-одиниці `quantity`, «k ∈ ℤ» біля поля й показ ключа після двох помилок (для `quantity` — «2 м 45 см»). Там само — звірка «підказка ≠ ключ»: приклади автоматично витягуються з усіх текстів, які дитина бачить у вправі (підказка під полем `SLID_ANS_UI.field` для класу й ключа вправи та тексти form/bad `SLID_LEARN.hintTexts`), і жоден не має зараховуватися як відповідь цієї самої вправи — для всіх answer-вправ змісту й fixture; тест падає, якщо витяг не знайшов відомих прикладів (`7/12`, `2 1/3`, `2,5`, `(3; −2)`, `3 ост. 2`, `7:05`…). `SLID_ANS_UI` — заморожена копія. Модульні випадки еквівалентних і неправильних записів — у `test-learn.mjs`. Аудит вважає формат матриці присутнім, якщо `answerKind` вправи має ту саму назву. Виняток (рішення людини 2026-10-31, tools-pqa-exactroot-in-list): вимогу `exactRoot` закриває також вправа `answerKind: "list"`, у ключі якої хоч один елемент — точний корінь (`√`, `∛`…; напр. «±√5», «2 ± √3», «0; √5»), якщо рушій справді перевіряє цей список точно: `SLID_LEARN.listKey` розбирає ключ тим самим `parseList`, що й `checkAns`, усі елементи канонічні, ключ як записано дає `ok`, а той самий список із десятковими наближеннями коренів — `bad`. Не рахуються: числовий list без кореня, list із десятковими наближеннями (`2,236; −2,236`), list лише з π. Так само (рішення людини 2026-10-31, engine-coordinates2-expression; `exprPair`) вимогу `expression` закриває вправа `answerKind: "coordinates2"`, у ключі якої хоч одна компонента — вираз зі змінною (`(p - m; k - n)`, №13.5(4)), якщо рушій справді перевіряє її як вираз: `SLID_LEARN.pairKey` розбирає ключ тим самим шляхом, що й `checkAns`, ключ канонічний (з `form` — сам проходить форму), ключ як записано дає `ok`, тотожний запис `0 + (…)` — не `bad`, а `(…) + змінна` і десяткове наближення `(…) + 0,0000001` — `bad`. Не рахуються: числова пара (`(-3; 1)`, `(√2; π)`), неканонічний ключ, не пара. Браузерна регресія `answer_format_checks` проводить пару виразів через екран: кнопки `^`, `·` і літери змінних, вставка літери в місце курсора, тотожний запис і `form`. Інші формати так не підміняються; драйвер реальних пулів вводить ключ як записано (масив `ratio` — через « : », `divrem` — «q ост. r»).

Введення `answer` з файла перевіряє технічне зарахування відповіді. Математичну правильність, відповідність джерелам, повноту методів і педагогічну опору перевіряє незалежний верифікатор. Інструмент перевіряє структуру URL/посилання на джерело; доступність і зміст URL він не засвідчує.
