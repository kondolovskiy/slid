# Бекенд

Код — `server/`. Запуск і команди — [server/README.md](../server/README.md).

## Принципи

1. **Застосунок лишається офлайн-першим.** Бекенд — необовʼязкове доповнення: синхронізація, кабінет учителя, аналітика, ШІ-тьютор. Без мережі все працює як зараз (ARCHITECTURE.md, D-002).
2. **Мінімум персональних даних дітей.** Учень — випадковий id; входи — анонімний токен пристрою, шкільний Google-акаунт (зберігаємо лише стабільний `sub` і домен школи) або код привʼязки. Імені, email і телефону сервер не просить і не зберігає; верхньорівневе поле `name` стану відкидає. Сам стан прогресу (клас `grade`, відповіді, бали, план) сервер зберігає — без нього синхронізація не має сенсу; за ним дитину не ідентифікувати. Нові поля стану з персональними даними — лише за рішенням людини в decisions.md.
3. **Модульний моноліт.** Один процес і одна БД, але модулі ізольовані так, ніби це окремі сервіси (нижче). Винесення модуля — це зміна адаптера, а не переписування.
4. **Мінімум коду, KISS, YAGNI.** Бібліотеки замість власних рішень; абстракція зʼявляється, коли є другий споживач. Сервер не дублює логіку, яка живе у фронтенді.
5. **TDD.** Спершу тест, що падає; модульні тести — на памʼятних адаптерах, e2e — лише на справжньому Postgres.

## Стек

| Що | Вибір | Чому |
|---|---|---|
| Мова, фреймворк | TypeScript, **NestJS 11** | Модулі й DI з коробки — саме те, що потрібно модульному моноліту; та сама мова, що й фронтенд (агенти й люди читають обидва боки; спільні контракти). |
| БД | **PostgreSQL 16** | `jsonb` для стану, транзакції, схеми на модуль. |
| Доступ до БД | **Kysely 0.28** | Типізований конструктор SQL і вбудований мігратор; без ORM-магії. 0.29 — лише ESM, з Jest і CommonJS Nest це зайвий клопіт. |
| Тести | Jest + Supertest | Стандарт Nest. |

**NestJS чи Go?** Для цих задач NestJS підходить: навантаження — дрібні JSON-запити, вузьке місце — БД, а не CPU. Go мав би сенс для важких потоків (стрімінг, тисячі WebSocket-зʼєднань на дешевому залізі) або якщо команда пише Go. Окремий модуль із такими вимогами можна написати на Go, коли його винесуть у сервіс, — контракт порту від мови не залежить. Мінус Nest — багато декораторів і шаблонного коду; тримаємо його в межах: без `@nestjs/config`, class-validator, ORM, CQRS-пакетів, доки вони не потрібні.

## Модулі

```
server/src/
  app.ts                 збирає модулі, CORS, ліміт тіла, /health
  db/database.ts         спільний пул Postgres (токен DB)
  db/migrate.ts          мігратор: кожен модуль — своя схема і своя таблиця міграцій
  ops/                   експлуатація (інфраструктура, як db/; глобальний OpsModule): JSON-логи, лічильники й сигнали,
                         /v1/admin/metrics, порт сховища лімітів RATE_LIMIT_STORAGE
  modules/<модуль>/
    index.ts             ПУБЛІЧНИЙ API: Nest-модуль, порти, міграції — більше нічого
    <модуль>.port.ts     контракт для інших модулів (інтерфейс + Symbol-токен)
    <модуль>.service.ts  логіка; залежить від портів сховища, не від Postgres
    *.store.ts           порт сховища + адаптери Pg… і Memory… (для тестів)
    *.controller.ts      HTTP
    migrations.ts        міграції схеми модуля
```

**Правила меж.** Автоматично перевіряє `server/test/architecture.spec.ts`:
- будь-який код (`modules/*`, `app.ts`, `db/*`) бачить модуль **лише** через його `index.ts` — для всіх форм імпорту (`from`, `import '…'`, `export … from`, `import()`, `require()`, будь-які лапки);
- `withSchema('…')` у модулі — лише рядковий літерал із власною схемою (`withSchema(змінна)` — помилка: тест не може її перевірити);
- рядок у коді модуля не називає **чужу** схему у формі `схема.обʼєкт`: `selectFrom('identity.learners')`, `insertInto`, `*Join`, `references('identity.learners.id')`, сирий `sql\`… from identity.learners\``, зокрема з квотованими ідентифікаторами (`"identity"."learners"`, `identity."tokens"`). Коментарі `//…` і `/*…*/` тест вирізає до пошуку рядків: непарний апостроф у коментарі (`// п'ять`) не ховає виклики після нього.

Домовленості, які тест не ловить (рев’ю):
- назву схеми не збирають динамічно (`${s}.learners`, конкатенація, `sql.raw(…)`, `sql.table(змінна)`) і не покладаються на `search_path` — тест бачить лише літерали;
- без регулярних виразів-літералів із лапкою чи `//` і без шаблонів, вкладених у `${…}`, у коді модулів: розбір коментарів у тесті їх не розуміє;
- залежність між модулями — через **порт** (інтерфейс + Symbol-токен), а не клас сервісу: `index.ts` експортує порт, не сервіс;
- кожен модуль має **свою схему Postgres** (`identity.*`, `progress.*`); сирий SQL у чужу схему й зовнішні ключі між схемами заборонені — звʼязок лише за id;
- міграції модуля лежать у модулі й мають свою таблицю `<схема>.kysely_migration`.

### Як винести модуль у сервіс

Приклад — `identity`. Споживач (`progress`) залежить від `IDENTITY: IdentityPort`.
1. Новий сервіс = тека модуля + його схема (переноситься `pg_dump -n identity`).
2. Поруч пишемо клієнтський Nest-модуль, що надає **той самий токен** `IDENTITY` (HTTP/gRPC-адаптер або локальна перевірка JWT) і `LearnerGuard`.
3. У `identity/index.ts` експортуємо `IdentityModule` = цей клієнтський модуль. `progress` імпортує `../identity` — його код не змінюється.

**Асинхронні події** (напр. «учня видалено» → видалити прогрес): коли зʼявиться перший такий випадок, додаємо порт `EventBus` з in-process адаптером (EventEmitter, а для надійності — таблиця outbox). При винесенні адаптер міняється на NATS/RabbitMQ. Зараз подій немає — шини теж немає (YAGNI).

## API v1

| Метод | Шлях | Що |
|---|---|---|
| `POST` | `/v1/learners` | новий анонімний учень → `{ id, token }`. Токен показують один раз; на сервері лише SHA-256. |
| `POST` | `/v1/auth/google` | `{ idToken }` (Google Identity Services) → `{ id, token }`. Лише акаунти Workspace з доменів `GOOGLE_DOMAINS`; особистий акаунт → 401. Домени порівнюються без урахування регістру. `{ idToken, link: true }` + `Bearer` анонімного учня без акаунта — привʼязує акаунт до нього (прогрес лишається); **лише після явного питання в інтерфейсі** («Це твій прогрес на цьому пристрої?»): на спільному шкільному ПК токен міг лишитися від іншої дитини. Без `link` — окремий учень. Якщо акаунт уже має учня — повертає його; клієнт зливає прогрес, як при 409. Google недоступний → 503. |
| `POST` | `/v1/pairing` | `Bearer` → `{ code, expiresAt }`: 6 символів без схожих (0/O, 1/I/L), 10 хв, одноразовий. |
| `POST` | `/v1/pairing/claim` | `{ code }` → `{ id, token }` того самого учня на новому пристрої; малі літери, пробіли й дефіс допустимі. Невідомий/прострочений → 401; 11-та спроба за хвилину з IP → 429. |
| `GET` | `/v1/me` | `Bearer` → `{ id, school }` (`school` — домен або `null`). |
| `GET` | `/v1/progress` | `Authorization: Bearer <token>` → `{ rev, data }` (`rev: 0, data: null` — ще нічого) |
| `PUT` | `/v1/progress` | `{ rev, data }` → `200 { rev+1, data }` або `409 { rev, data }` — поточна версія з сервера |
| `GET` | `/health` | `{ ok: true }`, перевіряє БД |
| `GET` | `/v1/admin/metrics` | `Bearer <ADMIN_TOKEN>` → `{ now, last, rules }`: лічильники поточного й попереднього вікна, правила сигналів. Без `ADMIN_TOKEN` (або коротшого за 32 символи) — 404; інший токен — 401 |

Кожен вхід видає **новий** токен пристрою (таблиця `identity.tokens`), тож пристрої незалежні. Ліміт частоти — 120 запитів/хв з IP на **кожен** ендпоінт identity окремо (клас школи виходить з однієї адреси), на `pairing/claim` — 10/хв. Лічильники в памʼяті процесу: при кількох репліках — спільне сховище (див. «Відкриті питання»). Код привʼязки, що випадково збігся з живим, сервер генерує заново (до 5 спроб); якщо всі зайняті — 503 («спробуй ще раз»), а не 500.
Лічильники лімітів зберігає порт `RATE_LIMIT_STORAGE` (`src/ops/rate-limit.ts`; контракт — інтерфейс `ThrottlerStorage` з `@nestjs/throttler`, тест контракту `rate-limit.spec.ts`). Зараз адаптер — памʼять процесу; спільне сховище = новий адаптер, що проходить той самий контракт, і заміна одного провайдера в `OpsModule`.

`data` — обʼєкт стану `localStorage["slid.v1"]` (ARCHITECTURE.md, «Стан користувача»), до 256 КБ і вкладеністю до 64 рівнів (глибше — 400: рекурсивні перевірки інакше переповнюють стек); `name` відкидається.

### Синхронізація: чому сервер не зливає

Стан — документ із версією (оптимістичне блокування, compare-and-set в одному SQL-запиті). Якщо два пристрої записали різне, другий отримує `409` з серверною версією, **зливає на клієнті** й повторює `PUT` з новим `rev`. Семантику злиття (бали за день сумуються з двох пристроїв, зірки — максимум, `errs` — обʼєднання за часом, плани за класами…) знає лише фронтенд, тож функція злиття житиме в `app/` як чиста функція з тестами поруч із `learn.js`. Сервер лишається тупим сховищем — і не треба тримати дві реалізації злиття.

## Спостереження: логи, лічильники, сигнали

Код — `server/src/ops/`. Без зовнішніх сервісів: stdout (його збирає Railway) і ендпоінт для адміністратора.

**Структуровані логи.** Кожен рядок — JSON (`ConsoleLogger` Nest у режимі `json`): `level`, `timestamp`, `context`, `message`. Події:
- `context: "http"` — один рядок на запит: `{ event: "http", method, route, status, ms, lh? }`. `route` — шаблон маршруту (`/v1/progress`), для незнайденого — `null` (сирий шлях і query не пишемо: там може бути що завгодно). `lh` — перші 16 hex **HMAC-SHA-256** від id учня з серверним ключем `LOG_HASH_KEY` (D-050 п. 5), якщо запит автентифіковано: звʼязує рядки одного учня, але id з логу не відновити, а маючи id (дамп БД, пристрій дитини), без ключа не знайти рядків цього учня в логах. Той самий ключ — той самий `lh`; заміна ключа розриває звʼязок зі старими рядками (ротація можлива, але лише свідомо). Ключ — `logHashKey` у `src/ops/log.ts`: заданий — ≥ 32 байти (UTF-8), інакше відмова старту; не заданий у production (`NODE_ENV=production`, так запускає `npm start`) — відмова старту; поза production (тести, розробка) — випадковий ключ процесу й попередження `warn` у контексті `ops`.
- `context: "metrics"` — підсумок вікна `{ event: "metrics", from, to, counts }` (рівень `log`) і сигнали `{ event: "alert", signal, count, of?, share? }` (рівень **`warn`**).
- Внутрішні повідомлення Nest і помилки 500 (зі стеком) — рівні `warn`/`error`, теж JSON.

**Чого в логах немає й не буде без рішення людини (AGENTS.md §4.12):** токенів, заголовків (`Authorization`, `User-Agent`), IP, тіла запиту й відповіді, стану прогресу, `learner_id` у відкритому вигляді, кодів привʼязки, Google `sub`/домену. Дозволені поля — `LOG_FIELDS` у `src/ops/log.ts` (unit і e2e перевіряють, що токена й id учня в лозі немає). Для solution-check — поля з docs/design/ai-solution-check.md §3.6.

**Лічильники** (`Metrics`, памʼять процесу, вікно — 1 година): `http`, `http.5xx`, `http.429`, `<METHOD> <route>`, `<METHOD> <route> <status>` (незнайдений маршрут — `*`); модуль може рахувати своє через `metrics.inc(назва)` (`Metrics` — глобальний провайдер `OpsModule`). Кінець вікна (і зупинка процесу) → рядок `metrics` і перевірка правил.

**Сигнали адміністратору** (`RULES` у `src/ops/metrics.ts`; спрацювання = рядок `warn` з `"event":"alert"`):

| `signal` | умова за годину | що означає |
|---|---|---|
| `server_errors` | 5xx > 1 % запитів і ≥ 5 | баг або БД недоступна |
| `throttled` | 429 > 5 % і ≥ 20 | ліміти душать клас за NAT або атака |
| `pairing_claim_failures` | ≥ 100 невдалих `pairing/claim` (401) | можливий розподілений перебір кодів |
| `google_unavailable` | ≥ 5 відповідей 503 на `auth/google` | Google недоступний або `GOOGLE_CLIENT_ID` не задано |
| `content_unknown` (додасть solution-check) | частка 422 `content_unknown` > 1 % або будь-які за 6 год після деплою Pages | розсинхрон змісту між Pages і сервером |

**Як адміністратор дізнається.** Зараз: фільтр у логах Railway за `"event":"alert"` (або рівнем `warn`) і `GET /v1/admin/metrics` з `ADMIN_TOKEN` для поточного вікна. Після першого деплою (рішення людини): куди доставляти сповіщення (сповіщення самого Railway — чи вміє він їх за логами, перевірити; email, Telegram) — це зовнішній канал, його підключаємо без зміни правил. Кілька реплік — у кожної свої лічильники; підсумовує той, хто читає логи (або спільне сховище разом із лімітами).

## Розгортання: Railway

Рішення людини 2026-11-01: для початку — [Railway](https://railway.com).
- Сервіс із кореневою текою `server/` (конфіг `server/railway.json`): збірка `npm run build`, перед кожним деплоєм `npm run migrate`, старт `npm start`, healthcheck `/health`.
- Postgres — сервіс Railway у тому самому проєкті; `DATABASE_URL` — посиланням на його змінну. `PORT` задає Railway. `CORS_ORIGINS` — адреса GitHub Pages застосунку.
- `GOOGLE_CLIENT_ID` — OAuth Client ID (Google Cloud Console, тип Web, authorized JavaScript origin — адреса застосунку); без нього `/v1/auth/google` → 503. `GOOGLE_DOMAINS` — домени Workspace шкіл через кому; порожньо — вхід через Google вимкнено.
- `LOG_HASH_KEY` — обовʼязковий секрет ≥ 32 байти (`openssl rand -hex 32`) для `lh` у логах (HMAC, «Спостереження»); без нього `npm start` (`NODE_ENV=production`) не стартує. Не міняти без потреби: нове значення — нові `lh`, старі рядки логу з новими не звʼяжуться. Зберігати лише в змінних Railway, не в репозиторії й не поруч із дампами БД.
- `ADMIN_TOKEN` — випадковий рядок ≥ 32 символів (напр. `openssl rand -hex 32`) для `GET /v1/admin/metrics`; без нього ендпоінт вимкнено (404).
- `TRUST_PROXY=1` на Railway (один проксі перед сервером) — щоб ліміти бачили справжній IP. Типово `0`: без проксі довіряти `X-Forwarded-For` не можна — його підробляють. Як саме Railway формує заголовок, перевірити після першого деплою: залогувати `req.ip` і `X-Forwarded-For` на тестовому запиті (див. «Відкриті питання»).
- Регіон — ЄС (дані дітей ближче до вимог GDPR і до України).

## Тести

- `npm run check` — типи, модульні тести сервісів на Memory-адаптерах, тест меж модулів. Без БД.
- `npm run test:e2e` — справжній Postgres, `DATABASE_URL` обовʼязковий: без нього тест **падає**, а не пропускається. Покриває міграції (двічі), 401, повний цикл запис/конфлікт, гонки паралельних вставок і оновлень, ізоляцію учнів, 400 (межі `rev`, `\u0000`, розмір, вкладеність 100 000) і 413, адаптер кодів привʼязки (збіг хешу), рядки логу без токена й id учня, `lh` = HMAC з `LOG_HASH_KEY` (однаковий для учня за того самого ключа, інший за іншого; production без ключа не стартує), `/v1/admin/metrics` (401/200), сигнал `alert`, ліміти через порт `RATE_LIMIT_STORAGE`.
- CI: `.github/workflows/server.yml` (сервіс `postgres:16`), запускається на зміни `server/**`; міграції проганяє з `dist` двічі, як на Railway.
- Памʼятні адаптери (`Memory…Store`) лежать поруч із Pg-адаптерами навмисно: реалізують той самий порт, а тест на порт бачить обидва.

## Що далі (кожне — окрема інженерна задача з незалежним рев’ю, D-026)

1. **Клієнт синхронізації у фронтенді**: функція злиття стану в `app/` (TDD), вмикання синхронізації в профілі, черга офлайн-записів. Без цього бекенд нікому не потрібен.
2. **Вхід у фронтенді**: кнопка Google Identity Services («Увійти шкільним акаунтом») і «Код для іншого пристрою» в профілі. Сервер готовий (identity: `/v1/auth/google`, `/v1/pairing`). Вихід/відкликання токена пристрою — коли знадобиться.
3. **Видалення даних** на запит (`DELETE /v1/learners/me`) — перший випадок для події між модулями.
4. **Захист**: структуровані логи, лічильники й сигнали, порт сховища лімітів — зроблено (server-hardening-2, «Спостереження»); решта — у «Відкритих питаннях».
5. **Кабінет учителя** (`classroom`): учитель з email, клас із кодом приєднання; учень приєднується кодом, не даючи імені (вчитель бачить псевдонім, який сам і задав).
6. **Аналітика кроків** (`analytics`): анонімні події «екран/відповідь/вихід» пакетами; окрема схема, згодом — окреме сховище.
7. **ШІ-тьютор** (`tutor`): проксі до моделі з контекстом кроку; ключ API лише на сервері.

## Рішення людини (2026-11-01)

- Хостинг — Railway.
- Пілот — школа з власним Google Workspace; SAML нам не потрібен. Якщо вхід не шкільним акаунтом — достатньо коду привʼязки.
- Одразу обидва входи: шкільний Google-акаунт і код привʼязки (уточнення того ж дня).
- Згода батьків: для шкільних акаунтів не потрібна окремо (дані веде школа); для особистих email — потрібна, тому їх поки не приймаємо.

## Відкриті питання до людини

- Що вчитель може бачити про дитину (Закон України «Про захист персональних даних», GDPR для ЄС).
- **Ліміти частоти (з server-hardening, рев’ю server-auth Б-2)** — потрібні дані або рішення:
  - скільки хопів у `X-Forwarded-For` на Railway і чи дописує проксі справжню IP — перевірити після першого деплою; від цього залежить `TRUST_PROXY`;
  - клас за одним NAT: 10 claim/хв і 120/хв на `auth/google` (уся школа о 8:30) — переглянути за даними пілоту;
  - захист від розподіленого перебору кодів: глобальний ліміт невдалих claim (ризик: зловмисник блокує привʼязку всім) чи довший код (8 символів ≈ 8,5·10¹¹ — довше вводити дитині); ліміт спроб на один код перебору не заважає (кожна спроба — інший код);
  - спільне сховище лімітів (Redis чи Postgres) — коли буде більше однієї репліки; Redis — додатковий сервіс і витрати на Railway. Порт `RATE_LIMIT_STORAGE` уже є: потрібен лише адаптер.
- **Канал сповіщень адміністратору** (після першого деплою): лишити фільтр логів Railway чи підключити зовнішній канал (email, Telegram), і хто адміністратор пілоту.
- **`nonce` для id_token (Б-6)**: захищає від повторного використання перехопленого токена (~1 год). Потрібні одноразовий nonce від сервера й підтримка в кнопці GIS, тож робити разом із входом у фронтенді («Що далі», п. 2), якщо людина вирішить, що ризик того вартий (за HTTPS і точного `aud` він низький).
